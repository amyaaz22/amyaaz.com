Using Zoho Catalyst Cache to Speed Up Deluge API Calls

Amyaaz AumeerSeptember 2024 · 5 min read

A common performance problem in Zoho implementations: a Deluge function that calls an external API on every single record save. At low volume, no problem. At scale, you hit rate limits and slow response times fast.

The Pattern

Catalyst's Cache segment is a managed Redis-compatible key-value store accessible from both Catalyst Functions and, via the Catalyst SDK, from Deluge. The strategy is straightforward: cache slow or rate-limited data at the Catalyst layer, refresh it on a scheduled basis, and let every Deluge call read from cache instead of hitting the external API directly.

How It Works in Practice

A Catalyst scheduled function runs every 30 minutes. It fetches the data that would otherwise be requested on every Deluge call - exchange rates, OAuth tokens, product price lists, tax rate tables, or any configuration data. That data is stored in Catalyst Cache with a TTL slightly longer than the refresh interval, ensuring there is always a valid value available. Each Deluge function then reads from cache in under 10 milliseconds instead of making a live API call that might take 800ms or trigger a rate limit error.

What This Solves

Instead of hitting an external API thousands of times per day, the external call happens once every 30 minutes. Rate limits disappear. Response times drop from hundreds of milliseconds to single digits. The Deluge function itself becomes more reliable because it no longer depends on an external service being available at the exact moment of execution.

Where to Apply This

This pattern is applicable to any data that is expensive to fetch but does not change on every request: OAuth tokens, currency exchange rates, product price lists, postal code lookups, tax rate tables, and application configuration values. If your Deluge function is fetching the same data on every execution, it almost certainly belongs in Catalyst Cache.
